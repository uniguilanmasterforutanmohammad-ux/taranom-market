# جوانه‌بازار — بازارچهٔ ماژولار کودکان و نوجوانان

پیاده‌سازی فاز ۱ و ۲ سند نیازمندی‌ها (`document.pdf`) با معماری کاملاً ماژولار: هر قابلیت یک ماژول مستقل است که
ادمین می‌تواند برای کل پلتفرم خاموش/روشن کند و هر کاربر (و والدین برای فرزندش) کلید شخصی دارد. اعمال محدودیت‌ها
هم در رابط کاربری و هم در API انجام می‌شود.

## اجرای سریع

```bash
docker compose up --build
```

سپس <http://localhost:3000> را باز کنید. سرویس `app` به‌صورت خودکار مایگریشن‌ها را اجرا و در صورت خالی‌بودن دیتابیس،
دادهٔ نمونه را می‌سازد.

### اجرای محلی (بدون Docker برای اپ)

```bash
docker compose up -d db redis
npm install
npx prisma migrate dev   # یا: npm run db:push
npm run db:seed
npm run dev
```

## معماری

- **Next.js 16 (App Router) + React 19 + Tailwind CSS 4** — رابط RTL با فونت وزیرمتن و تم کودک‌محور
- **PostgreSQL + Prisma 6** — مدل دادهٔ کاربر، رضایت، محصول، سفارش، اشتراک، ماژول و لاگ ممیزی
- **Redis** — محدودسازی نرخ ورود/ثبت‌نام و کش لیست محصولات (با fallback امن در صورت نبود Redis)
- **JWT در کوکی httpOnly + bcrypt** — نشست ۷ روزه و کنترل نقش‌ها
- **Docker Compose** — دیتابیس، ردیس و اپ

نقاط کلیدی پیاده‌سازی:

- `src/lib/modules.ts` — تعریف تک‌منبع ماژول‌ها، گروه‌ها، وابستگی پلن و قواعد ارزیابی
- `src/lib/module-service.ts` — وضعیت مؤثر ماژول (سراسری + کاربر + نقش + پلن) و گاردهای سرور
- `src/app/api/**` — اعمال `assertModule` و قواعد رضایت/سقف پلن در همهٔ مسیرهای حساس
- `src/app/dashboard/modules` / `src/app/admin/modules` / `src/app/parent` — سه سطح کنترل کلیدها
- `src/components/owl-logo.tsx` — لوگوی جغد سبز در حال مطالعهٔ کتاب (SVG اختصاصی)
- `src/components/contact-seller.tsx` + `src/app/api/messages` — فرم ارتباط با سازنده و ثبت ایمن پیام‌ها
- `src/lib/approval.ts` + `src/app/api/approval-requests` — چرخهٔ «درخواست اجازه از والدین» برای کلیدهای
  `messageReply` و `messageContact`

## قواعد ایمنی و حریم خصوصی

- ثبت‌نام کاربر زیر ۱۳ سال نیازمند **شمارهٔ موبایل والدین (اجباری)** و نام والد است؛ ایمیل والدین اختیاری است و
  ساخت رکورد رضایت `PENDING` انجام می‌شود. وصل‌شدن خودکار به حساب والد از روی ایمیل **یا موبایل** انجام می‌گیرد.
- **محصول کودک زیر ۱۳ سال** ابتدا در وضعیت `AWAITING_PARENT` ذخیره می‌شود (نه مسدود!)؛ والد در `/parent` آن را
  تأیید یا رد می‌کند و تنها پس از تأیید والدین با تگ «تأیید والدین» به صف بازبینی ادمین می‌رود. تأیید والدین
  همان لحظه رضایت را هم `APPROVED` می‌کند. خرید بدون تیک تأیید والدین همچنان در سرور مسدود است.
- لغو رضایت، محصولات کودک را از ویترین برمی‌دارد (`DRAFT`) و اعلان می‌فرستد.
- هیچ محصولی بدون تأیید ادمین عمومی نمی‌شود؛ تغییر محتوا محصول را به صف بازبینی برمی‌گرداند.
- ادمین در `/admin/moderation/[id]` می‌تواند متن، قیمت، نوع، دسته، برچسب و موجودی را ویرایش کند و همان‌جا
  تأیید یا رد کند (`POST /api/admin/review` با فیلد `edits`).
- وقتی سقف پلن پر شود، ورودی «ثبت محصول» از پنل کودک برداشته می‌شود و به‌جای فرم، کارت ارتقای پلن می‌آید؛
  کودک می‌تواند «درخواست ارتقا پلن» برای والدین بفرستد و تأیید والدین، پلن را فعال می‌کند (پرداخت نمایشی).
- لاگ ممیزی برای ورود، ثبت/تأیید/رد محصول، تغییر اشتراک و تغییر ماژول ثبت می‌شود.
- پیام کاربر زیر ۱۳ سال همیشه یک نسخه برای والدین (و اگر سازنده هم کودک باشد، والدین او) می‌گیرد و
  راه‌های ارتباطی والدین به کودک نشان داده می‌شود؛ ایمیل/تلفن کودکان هرگز نمایش داده نمی‌شود.
- هر پیام، ایمیل و موبایل پیام‌دهنده را همراه دارد (برای کودک، راه تماس والدین او) و والدین همیشه این
  اطلاعات را در `/parent` می‌بینند؛ نمایش آن به فرزند فقط با کلید `messageContact` از پنل والدین ممکن است.
- پاسخ‌دادن به پیام برای کاربران زیر ۱۸ سال تا زمانی که والدین کلید `messageReply` را روشن نکنند خاموش است؛
  والدین می‌توانند خودشان به‌جای فرزند پاسخ بدهند (پیام با برچسب «با نظارت والدین» ثبت می‌شود).
- فرزند می‌تواند از `/dashboard/messages` یا `/dashboard/modules` برای این دو کلید «درخواست اجازه» بفرستد؛
  درخواست در `/parent` تأیید یا رد می‌شود و تأیید، همان کلید ماژول را برای فرزند روشن می‌کند (لاگ + اعلان).
- **پروفایل کودک تحت مدیریت والدین:** والد می‌تواند از `/parent` برای فرزندش پروفایل بسازد بدون ایمیل، موبایل یا
  رمز عبور واقعی کودک (`User.managedByGuardian`). این پروفایل رمز قابل‌استفاده ندارد و ورودش در سرور مسدود است؛
  رضایت والدین هم‌زمان با ساخت پروفایل `APPROVED` می‌شود (روش `guardian`). همهٔ کارها — ثبت و ویرایش محصول، پاسخ
  به پیام و پیگیری — با حساب خودِ والد انجام می‌شود.
- والد می‌تواند از `/parent/children/[id]` محصول فرزندش را ثبت یا ویرایش کند. سرور بررسی می‌کند که واقعاً ولی او
  باشد، سقف پلن خودِ فرزند را لحاظ می‌کند و محصول را با `viaGuardian` و `submittedById` (حساب والد) ثبت می‌کند.
  ایمیل نمادین این پروفایل‌ها هرگز در رابط کاربری یا پنل مدیریت نمایش داده نمی‌شود.
- دادهٔ پرداخت در این نسخه شبیه‌سازی شده و هیچ شمارهٔ کارت واقعی ذخیره نمی‌شود.

## قواعد داده و عملیات مخرب

> ⚠️ **دادهٔ کاربران هرگز پاک نمی‌شود.** جزئیات و قانون کامل در `AGENTS.md` (قانون ۱) آمده است.

- `node prisma/seed.mjs` روی دیتابیسی که داده دارد **اجرا نمی‌شود**؛ گارد داخلی آن را متوقف می‌کند و فقط با
  `ALLOW_WIPE=true` (npm script: `db:seed:force`) و تأیید صریح کارفرما اجازهٔ پاک‌سازی می‌دهد.
- قبل از هر پاک‌سازی، یک اسنپ‌شات JSON از همهٔ جدول‌ها در `backups/` ذخیره می‌شود.
- بکاپ دستی/فشرده در هر زمان: `npm run db:backup` (خروجی `pg_dump` در `backups/`، نگه‌داری ۱۰ نسخهٔ آخر).
- تغییر ساختار داده فقط با فایل مهاجرت افزایشی (`prisma/migrations/...` + `prisma migrate deploy`)؛
  `migrate reset`، `db push --force-reset` و `docker compose down -v` در این پروژه ممنوع است.
- پیشنهادهای تأییدنشده (از جمله بکاپ زمان‌بندی‌شده و اسکریپت بازیابی) در `docs/backlog.md` ثبت می‌شوند.
· `POST /api/admin/purchase-mode` · `POST /api/messages` · `POST /api/messages/reply`

## دستورها

```bash
npm run dev            # توسعه
npm run build          # تولید (prisma generate + next build)
npm run db:migrate     # مایگریشن توسعه
npm run db:seed        # دادهٔ نمونه (⚠️ داده‌های فعلی را بازنویسی می‌کند)
npm run db:studio      # Prisma Studio
```
